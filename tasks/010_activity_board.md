# Задача: доска «что активно» — события с датами из разговоров

Цель: таблица/календарь событий (минты, клеймы, вайтлисты, тестнеты, снапшоты, TGE, дедлайны), извлечённых из чата, со статусом «скоро / идёт / прошло» и ссылками на разговоры.

Создай `extract_events.py`; меняй `app/server.py`, `app/index.html`; можно добавить команду в `build_vault.py` НЕ нужно — заметку для Obsidian пишет сам extract_events.py. Не читай `.llm_env`/`.openrouter_key`, не читай `tasks/*.log`, НЕ открывай PNG.

## 1. `extract_events.py` (LLM: DeepSeek через модуль проекта `llm`)
- Источник: `data/kb.sqlite`, полезные разговоры `convs WHERE verdict != 'drop'` (1578). Материал разговора: дата начала, выжимка `summary`, `scheme_summary`, и ключевые сообщения (`key_msgs` — JSON-список id; тексты из `messages` + `media_text` JSON `[{kind,text}]`, каждый ≤500 символов) с датой-временем каждого сообщения (`ts`). Посмотри функцию `conv_material` в `build_vault.py` для примера — но НЕ импортируй build_vault (он тянет лишнее), напиши свою компактную.
- Пачки по ~12 разговоров (≤25k символов). Вызов: `llm.chat_json(llm.WRITER, SYS, user, max_tokens=8000, temperature=0.1, fallback=llm.ENTITY)`. Параллельность `ThreadPoolExecutor(3)` (у провайдера лимит 3 параллельных запроса — больше нельзя).
- SYS (по-русски): извлечь только КОНКРЕТНЫЕ события с датой или сроком; относительные даты («завтра», «в пятницу», «через 2 дня») переводить в абсолютные по дате сообщения; если дата неизвестна — не выдумывать (date=null, но событие брать только если есть явный срок/окно: «клейм открыт до…», «минт сегодня»). Не включать реферальные ссылки/коды, адреса кошельков, ключи. Формат ответа:
  `{"events":[{"conv":"<id разговора из материала>","type":"mint|claim|whitelist|testnet|snapshot|tge|airdrop|deadline|launch|other","project":"…","title":"коротко что за событие, ≤90 симв","date":"YYYY-MM-DD|null","end_date":"YYYY-MM-DD|null","time":"HH:MM UTC|null","chain":"…|null","details":"1–2 предложения: условия, цена, количество, как участвовать","msg_ids":[…]}]}`
  Идентификаторы разговоров давай модели короткими алиасами (e1..eN) и переводи обратно, чтобы она не путала длинные id.
- Кэш/resume: результат каждой пачки сохраняй в `data/events_raw/<хеш списка conv>.json`; повторный запуск не зовёт LLM для готовых пачек.
- Валидация: conv должен быть из пачки, msg_ids — из ключевых сообщений этого разговора (иначе выкинуть id), дата — валидная и в диапазоне 2026-01-01…2027-12-31.
- Дедупликация: нормализуй project (lower, без пробелов/пунктуации) + type + date; одинаковые — слить в одно событие с несколькими источниками (`sources: [{id: "<short>-<conv>", msg_ids}]`), details — самый длинный.
- Таблица `events(eid INTEGER PRIMARY KEY, type, project, title, date, end_date, time, chain, details, sources TEXT /*JSON*/, first_seen TEXT)` (пересоздавать). `<short>` — как в SHORT из app/server.py.
- Заметка Obsidian `vault/Календарь активностей.md`: по месяцам (новые сверху), строки `- **YYYY-MM-DD** · тип · **Проект** — title [[<short>-<conv>]]`. Ссылки на разговоры должны совпадать с файлами в `vault/Источники/<short>/<short>-<conv>.md` (проверь существование, несуществующие не ставить).
- Флаг `--limit N` — обработать только N пачек (для пробы). Печать: пачек, событий сырых → после слияния, по типам, usage (`llm.usage`).

## 2. Сервер
`GET /api/events?type=&q=&chain=` → список событий с полями таблицы + `status`: относительно сегодняшней даты (`datetime.date.today()`): `soon` (date в будущем ≤14 дней), `future` (>14 дней), `active` (date ≤ сегодня ≤ end_date), `past`; без даты — `undated`. Сортировка: active, soon, future по возрастанию даты; past по убыванию. Также верни `today` и дату последнего сообщения в базе (`max(ts)` из messages) — данные из экспорта, после неё событий нет.
