# Задача: поиск по смыслу без внешнего шлюза + ключевые слова через LLM

Не читай `.llm_env`/`.openrouter_key`, не читай `tasks/*.log`, НЕ открывай PNG. Меняй: новый `embed_local.py`, `app/server.py`, `build_fts.py`, `requirements` не нужен (пакеты ставь pip).

## Проблема
Смысловой поиск зависит от шлюза HCNSEC (OpenCode API Manager, `embed.py`, Qwen3-Embedding-8B 2048-d) — он часто не отвечает, тогда поиск работает только по словам, а FTS цепляется за стоп-слова: на вопрос «Какие антидетекты советовали для мультиаккаунтов?» нашлись разговоры по словам «какие» и «для», ни одного про антидетекты. Чат из-за этого отвечает плохо.

## 1. Локальные эмбеддинги — `embed_local.py`
- Модель: `intfloat/multilingual-e5-small` (384-d) через `fastembed` (ONNX, без torch): `pip install fastembed`. Python здесь x64 под эмуляцией на ARM — onnxruntime win_amd64 работает. Если fastembed не поддерживает эту модель — используй ту же модель через `onnxruntime` + `tokenizers` напрямую (ONNX-файлы с Hugging Face, например `Xenova/multilingual-e5-small`, quantized). Важно: та же модель должна работать в браузере через transformers.js (`Xenova/multilingual-e5-small`) — это понадобится архиву (задача 023), поэтому выбирай вариант, совместимый по векторам (тот же токенайзер и pooling: mean pooling + L2-нормировка, префиксы e5: `"passage: "` для документов, `"query: "` для запросов).
- Документ разговора — тот же, что строит `embed.doc()` (импортируй функцию `doc` из embed.py или повтори), обрезка по 512 токенам модели.
- Таблица `emb_local(topic, conv, vec BLOB float32)` для всех полезных разговоров (1578) + `emb_art(path, chunk, vec)` для кусков статей из `fts_art` (если таблица есть). Resumable, пачками, прогресс в консоль; замерь время.
- Функция `embed_query(text) -> np.ndarray` с кэшем модели в памяти (загрузка один раз).

## 2. Сервер
- `search()`/`hybrid_search()`: смысловая часть — по `emb_local` через `embed_local.embed_query` (локально, без сети, должно занимать < 1 с после прогрева; прогрев модели при старте сервера в фоне). Шлюз HCNSEC больше не использовать в поиске (embed.py оставить как есть для истории).
- **Стоп-слова в FTS**: список русских и английских служебных слов (какие, какой, что, как, для, про, это, есть, был, были, кто, где, когда, ли, или, и, в, на, с, по, о, об, у, к, от, до, за, из, не, а, но, же, бы, мне, нам, вы, мы, они, он, она, the, a, an, to, of, for, and, is, what, how и т.п. — ~120 слов) выкидывать из FTS-запроса; слова короче 3 символов — тоже (кроме чисел и латинских тикеров из 2+ заглавных).
- **Ключевые слова через LLM** (для чата и для поиска из чата): перед поиском короткий вызов `llm.chat_json(llm.WRITER, …, max_tokens=300, temperature=0)` → `{"query": "переформулированный самостоятельный вопрос", "keywords": ["антидетект", "AdsPower", "Dolphin", "мультиаккаунт", "профили браузера", ...]}` — 5–12 ключевых слов и близких терминов/названий, которые реально встречаются в крипто-чатах (включая английские названия и сленг). FTS-запрос строится из keywords (OR, префиксы), смысловой — по `query`. Объедини с существующей переформулировкой для уточняющих вопросов (один вызов, а не два). Кэш по тексту вопроса. Если LLM недоступен — FTS по словам вопроса без стоп-слов.
- Ранжирование RRF как сейчас; добавь небольшой бонус разговорам, где совпало ≥2 разных keywords.
- `/api/search` (кнопка «Показать все» и прямые запросы) — тоже со стоп-словами и локальными эмбеддингами; LLM-расширение — только если передан `expand=1` (чат передаёт).
