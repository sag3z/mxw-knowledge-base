# Настройка VPS с нуля: пользователь, SSH-ключи, fail2ban и ufw

- Источник: ветка ai_вайбкод_билдинг_хакатоны, сообщение #60967, video_files
- Категория: ai_dev
- Теги: vps, ubuntu, ssh, fail2ban, ufw, linux, sudo, администрирование

## Кратко
Видео-скринкаст (речь и экран) о первом подключении к VPS: 1 vCPU, 1 ГБ RAM, Ubuntu 24.04, регион Франкфурт. Автор — девушка-стример, опыт называет очень небольшим. Главный вывод: базовая защита сервера — отдельный пользователь с sudo, вход по ключу, fail2ban и ufw — сделана, но ход видео полон ошибок и паники, и сама запись стоит рассматривать как пример того, чего не делать.

## Главное
- Подключение под root по паролю, проверка ОС, `apt update` и `apt upgrade` (на момент записи было 68 пакетов к обновлению).
- Создание пользователя через `adduser`, добавление в группу sudo (`usermod -aG sudo`). Пароль пропускать не стоит — автор сама это отметила.
- Генерация ключа ED25519 на локальной машине и копирование через `ssh-copy-id -i`. Первая попытка дала «Permission denied», потом ключ добавился.
- Вход по ключу: проверка через `ssh -i`, затем выключение парольной аутентификации в конфиге sshd. Предупреждение из видео: в `/etc/ssh/sshd_config.d/50-cloud-init.conf` стояло `PasswordAuthentication yes`, поэтому такие файлы надо проверять (`sshd -T`), а не править только один.
- Перезапуск sshd. После запрета root-доступа и отключения пароля текущая сессия перестала давать root-права; автор отметила, что это была её ошибка при ограничении доступа.
- Установка fail2ban; в `/etc/fail2ban/jail.d/sshd.local`: `[sshd]`, `enabled = true`, `backend = systemd`, `maxretry = 5`, `findtime = 10m`, `bantime = 2h`. Проверка `fail2ban-client -t`, затем `systemctl enable --now fail2ban`. Через некоторое время в статусе sshd уже был один забаненный IP и 89 неудачных попыток.
- Firewall ufw: `ufw allow 22/tcp`, `ufw default deny incoming`, `ufw default allow outgoing`, `ufw enable`. Предупреждение ufw: включение может разорвать существующие SSH-подключения. Порт проверяется командой `sshd -T | grep '^port '`.
- Автор отметила, что при переходе с root на пользователя встретились ошибки `Permission denied` на `apt` и неверный пароль sudo.
- Итоговые проверки: `uptime`, `free`, `df`. Нагрузка 0,00, памяти 1 ГБ, места мало. Docker автор считает излишеством для такого сервера.
- Совет из видео: если хочется поставить защиту SSH на уровне OpenSSH, встроенного аналога fail2ban в sshd нет — нужен отдельный инструмент.
- Ошибки на записи, которые стоит учесть: выключение парольной входа без проверки ключа может закрыть доступ; `ufw enable` по SSH без правила для порта 22 отрезает подключение.
