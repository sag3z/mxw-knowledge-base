# Задача: поиск не должен зависать, когда шлюз эмбеддингов тормозит

Меняй только `app/server.py` (embed.py не трогай — он нужен для пакетной индексации). Не читай `.llm_env`/`.openrouter_key`, не читай `tasks/*.log`, НЕ открывай PNG.

Проблема: `search()` зовёт `embed.embed([q])` — там `timeout=300` и 5 повторов с паузами. Шлюз HCNSEC (OpenCode API Manager, 127.0.0.1:43117) сейчас отвечает на один эмбеддинг ~50 с, иногда виснет — `/api/search` и чат ждут минутами.

Сделай в server.py свою функцию эмбеддинга запроса:
- один HTTP-запрос к тому же эндпоинту (`embed.BASE + "/embeddings"`, `embed.MODEL`) с таймаутом 12 с, без повторов;
- кэш результатов по тексту запроса (LRU на 500, `functools.lru_cache` или dict) — повторный поиск того же запроса и переформулировки в чате мгновенны;
- «автомат»: после неудачи (таймаут/ошибка) 60 секунд вообще не пробовать эмбеддинг (сразу FTS-only, `semantic:false`), потом снова пробовать;
- при неудаче — поиск только по словам (это уже поддержано: флаг `semantic:false`, фронт показывает предупреждение). Проверь, что и чат, и дайджест, и события/поиск в панели работают в этом режиме.
- Опционально: прогрев — при старте сервера в фоновом потоке сделать один эмбеддинг «тест», чтобы первый поиск не платил за холодный старт.

Проверка: перезапусти сервер отвязанно (`Start-Process -WindowStyle Hidden python -ArgumentList '-u','app/server.py','8765'` с рабочей папкой проекта; старый процесс останови). Замерь время `/api/search?q=антидетект` 2 раза подряд (второй — из кэша). Сымитируй недоступный шлюз (временно подмени BASE на несуществующий порт в отдельном тестовом инстансе сервера на другом порту, например 8799) — поиск должен ответить за ≤13 с с `semantic:false`, следующий — сразу. В отчёте — замеры.
